
# 基础RAG（Naive RAG）
——大模型增强检索的第一步

## 本节重点

- **课程目标**：理解基础RAG的核心思想、工作流程、局限性及其历史意义。
- **核心问题**：如何让大模型“学会”检索外部知识，从而减少“胡说八道”？
- **关键概念**：检索增强生成 (RAG)、向量化、向量数据库、索引-检索-生成范式。

---

## 第一部分：为什么需要RAG？—— 大模型的“先天不足”

### 场景举例
> **场景**：你的朋友问你一个专业问题（比如“猫吃了绿萝会不会中毒？”），一个**从未联网更新过知识**的“学霸”和一个**可以随时查阅图书馆**的“研究员”，谁的答案更可靠？

### 1.1 纯大模型的困境
-   **知识是“静态”的**：知识来源于训练数据，一旦训练完成，知识就“冻结”了。
-   **无法获取新知识**：对于训练后发生的事件或冷门知识，模型一无所知。
-   **产生“幻觉”**：在不确定时，模型倾向于编造“听起来合理”的错误答案，而不是说“不知道”。
    -   **案例**：模型可能错误地回答“绿萝对猫通常无毒”，而**事实是有毒的**。这在医疗、法律等严肃场景下是致命的。

### 1.2 RAG的解决方案：为学者配一座“图书馆”
-   **核心思想**：**先查后答，按图索骥**。模型不再仅凭“记忆”回答，而是先从一个外部知识库中**检索**相关信息，再基于这些信息**生成**答案。
-   **效果**：答案更**准确、具体、可追溯**，极大缓解了幻觉问题。

## 第二部分：解剖基础RAG (Naive RAG) —— 一个朴素的“图书馆”

### 核心概念：Naive RAG
-   **定义**：RAG技术最原始、最基本的形态。它确立的“**检索-生成**”协同范式，是所有后续高级RAG技术的基石。
-   **关键词**：**简单、直接、三步走**。

### 2.1 三大核心步骤：一个完整的案例

**案例问题**：“我的猫吃了绿萝会中毒吗？”

#### **步骤一：索引 (Indexing) —— 离线“藏书”**
> 目标：把知识库（文档）加工成计算机易于检索的格式。

1.  **文档解析**：读取原始文档（如PDF手册），提取纯文本。
    -   *原文片段*：“绿萝对猫有毒。其汁液中含有不溶性草酸钙结晶，猫误食后会出现口腔刺激、流涎、呕吐等症状...”
2.  **文本分块 (Chunking)**：将长文本切分为语义完整的短文本块。
    -   *为什么要切？*
        -   **模型上下文限制**（传统原因）。
        -   **更重要的原因：检索精度**。如果把整本书压缩成一个向量，细节信息会丢失。分块让每条知识都有自己独立的、高精度的“语义坐标”。
    -   *切分后示例*：
        -   块1：“绿萝（Epipremnum aureum）对猫有毒。其汁液中含有不溶性草酸钙结晶。”
        -   块2：“猫误食后会出现口腔刺激、流涎、呕吐等症状...”
3.  **向量化 (Vectorization)**：调用**嵌入模型**，将每个文本块转换为一个“向量”（一串代表语义的数字）。
    -   *关键理解*：向量是文本在**语义空间中的坐标**。语义越相近，坐标距离越近。
    -   块1向量：`[0.023, -0.411, 0.892, ...]`
    -   块2向量：`[0.019, -0.398, 0.905, ...]` (与块1距离近)
4.  **存储**：将“文本块-向量”对存入**向量数据库**。该数据库擅长快速查找与给定向量最相似的向量。

| 离线阶段 | 输入 | 处理 | 输出 |
| :--- | :--- | :--- | :--- |
| **索引** | 原始文档（PDF/TXT） | 解析 → 分块 → 向量化 | 向量数据库 |

#### **步骤二：检索 (Retrieval) —— 在线“查书”**
> 目标：根据用户问题，从“图书馆”中快速找到最相关的“书页”（文本块）。

1.  **查询向量化**：使用**同一个嵌入模型**，将用户问题也转换为向量。
    -   *关键*：必须用同一模型，确保查询和文档在同一个语义空间。
2.  **相似度匹配**：拿着查询向量去向量数据库中搜索，找出**距离最近**（语义最相似）的K个文本块（例如Top-3）。
    -   结果示例：
        -   块1（距离0.102）：绿萝有毒...
        -   块2（距离0.115）：误食症状...
        -   块3（距离0.143）：急救方法...

| 在线阶段（检索） | 输入 | 处理 | 输出 |
| :--- | :--- | :--- | :--- |
| **检索** | 用户查询 | 向量化 → 相似度搜索 | 相关文本块列表 |

#### **步骤三：生成 (Generation) —— 基于资料“作答”**
> 目标：让大模型基于检索到的资料，生成最终答案。

1.  **构建提示词 (Prompt)**：将**用户原始问题**和**检索到的文本块**拼接成一个结构化的提示。
2.  **调用大模型生成**：将提示词发送给大模型，要求它**仅基于**提供的资料回答。
    -   **提示词示例**：
        > 请**仅基于以下参考资料**回答用户问题。如果参考资料中没有答案，请明确告知。
        > 
        > **参考资料：**
        > [1] 绿萝对猫有毒...草酸钙结晶。
        > [2] 误食症状：口腔刺激、流涎...
        > [3] 急救建议：清水冲洗口腔，联系兽医。
        >
        > **用户问题：** 我的猫吃了绿萝会中毒吗？
3.  **获得答案**：模型生成准确、具体的回答，并追溯到资料来源。
    -   **RAG回答**：“是的，绿萝对猫有毒...建议您立即用清水冲洗猫咪口腔，并尽快联系兽医。”

| 在线阶段（生成） | 输入 | 处理 | 输出 |
| :--- | :--- | :--- | :--- |
| **生成** | 用户查询 + 检索到的文本 | 构建提示词 → LLM生成 | 最终答案 |

#### **Naive RAG完整流程总结图 (文字描述)**
`用户提问` → `[检索阶段]` 问题向量化 → 在向量数据库中搜索 → 召回Top-K相关文本块 → `[生成阶段]` 将问题和文本块拼接成提示词 → 大模型生成最终答案 → `输出回答`

## 第三部分：Naive RAG的局限 —— “原始图书馆”的烦恼

### 三个核心问题

1.  **检索质量不稳定**
    -   **问题**：向量相似度 ≠ 逻辑相关性。口语化、模糊的提问会导致检索到语义相似但无关的内容。
    -   **致命伤：多跳推理 (Multi-hop Reasoning)**
        -   *复杂问题示例*：“让我朋友那只猫中毒的那种植物，原产地是哪里？”
        -   *Naive RAG的失败*：它会直接搜索整个句子，无法先推理出“植物=绿萝”，再查询“绿萝原产地”。这种链式推理，Naive RAG无能为力。

2.  **生成质量受制于检索质量 (Garbage in, Garbage out)**
    -   **问题**：Naive RAG**完全信任**检索结果。如果召回的是噪音或错误信息，模型会基于这些信息“自信地”生成错误答案。
    -   **表现**：回答可能碎片化、缺乏逻辑衔接。

3.  **缺乏自我纠错和动态更新能力**
    -   **问题**：流水线作业，一旦跑完，结果直接输出。**没有检查机制**，也无法在生成过程中根据初步结果调整检索策略。
    -   **知识滞后**：知识库是离线更新的。新知识无法即时生效。

### 这些短板问题催生了后续技术的演进方向
-   **检索不准** → **重排序 (Rerank)**、**查询重写 (Query Rewriting)**
-   **缺乏纠错** → **Agentic RAG** (让AI能自我反思、主动重新检索)
-   **知识滞后** → 实时检索、知识图谱 (GraphRAG)

## 第四部分：历史意义与总结

### Naive RAG的伟大之处：伟大的第一步

-   **开创性范式**：首次验证了“**检索-生成**”协同框架的可行性，将“**知识存储**”与“**语言推理**”解耦。
-   **低成本知识更新**：更新知识只需重新索引文档，**无需重新训练/微调**大模型，成本从数百万美元降至接近零。
-   **提升可解释性**：答案可以**追溯到具体的参考资料**，这在医疗、金融、法律等需要“审计”的领域至关重要。
-   **奠定技术基石**：为今天RAG生态中的向量数据库、混合检索、知识图谱等所有技术提供了最初的“骨架”。

#### **核心回顾**
1.  **一句话总结Naive RAG**：一个简单、朴素的“**先查后答**”方案，通过**索引 -> 检索 -> 生成**三步，有效缓解了模型幻觉和知识滞后问题。
2.  **三个关键词**：**分块**、**向量化**、**向量数据库**。
3.  **三个局限**：检索质量不稳、生成质量受制于检索、缺乏自我纠错。
